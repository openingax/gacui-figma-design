# 日志问题中心

问题中心兼容旧日志，无需等待所有客户端升级。原始事件只读；每个问题的处理记录保存在日志数据目录 `issues/<稳定ID>/<修订号>.json`，应与原始日志一起备份，不能放进会被部署替换的代码目录。

## 三个独立事实

- 错误发生次数：历史实际发生的事件，处理完成后不会消失；包括等待事件的旧原始错误。
- 问题处理状态：待处理 → 处理中 → 已修复待验证 → 已关闭，可重新打开。
- 任务执行和交付：继续按日志与可关联验证回执判断；人工关闭 Issue 不改任务事实，更不代替用户验收。

同设备、任务、操作、阶段、目标、确认版本与具体诊断相同的错误归并；仅有 unexpected 等泛化错误码时按执行批次隔离。不删节点数字、路径来强行归并。业务等待、缺少目标单列待跟进。帮助命令采用既有可关联过滤。

## 更新和关闭

正式网页在“问题中心”或任务、使用者详情里打开问题。填写操作人、处理说明，可设置负责人、修复版本或提交、验证依据。当前使用共享访问口令，操作人是自填身份，不声称经过个人认证。

“已修复待验证”需填写修复版本或修复依据；不能因为服务器发版就认为同事已升级。“已关闭”必须选择已验证、误报、重复或无需处理，并留下依据；重复必须关联已有的非重复问题。旧版本问题修复后仍需记录升级和实际验证结果。

同一工作流的可靠交付回执可自动标记已恢复；没有关联的旧日志、普通 status 成功、规划成功或设备画像版本更新均不能自动关闭。手工记录优先，不因日志推断覆盖。

已关闭问题出现时间更晚的新失败会重新打开，旧关闭依据仍可查看；晚到的旧事件不会算复发。客户端时钟会影响先后判断，时间不可信时应人工核对，不把未收到事件视为成功。

## 运维与兼容

- `5190` 本机看板只读显示问题；正式网页在 logs 模式提供同源认证写入。snapshot 模式只读。
- 写入要求已登录 Cookie、同源 Origin、JSON 和自定义请求头。请求有大小限制。页面携带版本摘要，处理记录或事件已变化时返回409，保留编辑内容并提示重新核对。
- 每次操作追加完整独立文件，原子发布，不覆盖已有修订。读取不产生文件。损坏记录拒绝展示，不能静默回退成未处理。
- 无数据库或外部 Issue 平台依赖。不向 GitHub/Gitee 上传客户问题内容；这些平台仍只承载审核过的源码和发行物。
- 部署回退只切代码，不删除 `issues/`。旧看板可能不显示处理进度，升级后仍可读取。复原备份时需同时保留完整修订链。
